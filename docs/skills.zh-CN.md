# 内置技能

[English](skills.md) | **简体中文**

应用内置两个技能，二者构成一个闭环：**`ai-usage-review`** 找出花钱的地方，
**`ai-change-impact`** 验证修复是否奏效。两者都读取 [MCP 服务器](mcp.zh-CN.md)，
且都不写入 —— 它们只负责建议，由你的助手用自己受权限管控的编辑工具落地。

之所以拆成两个技能：它们的触发语境互不相交 —— 一个在改动之前问，一个在改动之后问。
一个同时覆盖两者的技能，结果会是两边都触发不稳。

---

## 安装与更新

两个技能都在启动时安装到检测到的每个 AI 工具的用户级 skills 目录 —— Claude Code 为
`~/.claude/skills/ai-usage-review/` 与 `~/.claude/skills/ai-change-impact/`。源文件位于
[`assets/skills/`](../assets/skills/)：在那里编辑，重启应用即可推送更新。首次安装后
重启一次你的 AI 工具，它才会加载这两个技能。

用 `--no-provision` 可关闭；`/mcp` 端点仍然提供服务。

## `ai-usage-review`

### 如何调用

用 `/ai-usage-review`，或者直接问。技能按你真实会输入的说法触发：

| 你想要 | 这样问 |
|---|---|
| 完整复盘 | `/ai-usage-review` |
| 收窄范围的复盘 | `/ai-usage-review 为什么我的会话这么贵？` |
| 聚焦成本 | *“什么最花钱？”*、*“帮我降低 token 开销”* |
| 解释某个症状 | *“老是上下文不够”*、*“老是问我要权限”*、*“它不听我的规则”* |
| 一个设计决策 | *“这个该做成 skill 还是 hook？”*、*“什么该放进 CLAUDE.md？”* |
| 技能不触发 | *“我的 skill 为什么不触发？”* |

明确说出症状是值得的 —— 技能会把抱怨映射到能解释它的检查项，优先从那里入手，
而不是把 11 项检查全走一遍。

### 它做什么

1. 先确定要看哪个 provider（`list_providers`），再为之后每次调用指定作用域。
2. 按固定顺序采集 —— 支出形态 → 浪费信号 → 单会话细节 → 常驻上下文 → 扩展项 ROI →
   确定性缺口 → 正确性 —— 一旦结论有了支撑就停止采集。
3. 执行 `references/playbook.md` 中的 11 项检查，每项都有测量值、阈值、修复方案，以及
   一条“如何用真实数字估算节省”的规则。
4. 输出至多 7 条按预估节省排序的发现，每条都注明数据来自哪次工具调用，并以“先做这件事”
   收尾。
5. 主动提出用你助手自己的编辑工具落地其中机械性的改动。

### 检查清单

| # | 检查 | 触发条件 |
|---|---|---|
| C1 | 指令文件对每个回合征税 | 单文件超过约 2,000 token，或窗口内注入超过 200 万 token |
| C2 | 高价模型在做常规工作 | 高价档占 token 超过 50% |
| C3 | 提示缓存没命中 | 整个窗口低于 50%；单次运行低于 30% |
| C4 | 会话携带过多上下文 | 单次调用超过 20 万 token，或单次运行占该周期 20% 以上 |
| C5 | 不划算的技能 | 窗口内零调用、被同名高优先级定义遮蔽，或正文很大而使用很少 |
| C6 | MCP 服务器入不敷出 | schema 超过 2,000 token 且零调用；探测报错 |
| C7 | 该做成 hook 的规则；已死的 hook | 散文里的“总是/绝不”规则；零触发的 hook |
| C8 | 应该沉淀为技能的重复劳动 | 同一形态任务在窗口内出现 3 次以上 |
| C9 | 子智能体开销过重的运行 | 子智能体占单次运行 token 超过 60% |
| C10 | 权限白名单过窄 | 日常高频命令不在 `allow` 中 |
| C11 | 形同虚设的设置 | 键落在不被读取的层、被遮蔽的命令/技能、孤儿记忆文件 |

### 一条发现长什么样

每条发现都带着它依据的测量值，让你可以核对而不是选择相信：

```
### 全局 CLAUDE.md 在对每个回合征税 —— 约 $41/月
**测量值：** list_instruction_files —— ~/.claude/CLAUDE.md 有 3,180 token，
在 30 天窗口内被注入了 410 万次。
**为什么花钱：** 它位于每个会话每次请求的前缀中，因此成本是 token × 请求数，
而不是 token × 会话数。
**修复：** 把那四步带编号的发布流程移进一个 skill；保留构建命令和分支命名规则。
约减少 1,700 token。
**工作量：** 10 分钟
```

报告以一行**先做这件事**收尾，指出节省与工作量之比最高的那项；再用一行说明检查过
但结果健康的部分 —— 这样你知道“没有发现”是测出来的，不是跳过的。

### 文件

```
assets/skills/ai-usage-review/
  SKILL.md                 工作流：定范围 → 采集 → 诊断 → 报告 → 落地
  references/
    playbook.md            11 项检查：信号、阈值、修复、如何估算节省
    authoring.md           如何构建修复方案：skill / hook / 子智能体 / CLAUDE.md 怎么选
```

`SKILL.md` 刻意保持简短 —— 技能正文一旦加载，就会在该回合剩余部分一直留在上下文里。
两份 reference 仅在需要时才读取。

## `ai-change-impact`

### 如何调用

| 你想要 | 这样问 |
|---|---|
| 让它自己选模式 | `/ai-change-impact` |
| 对比两次指定会话 | `/ai-change-impact r-9f3a r-4d81` |
| 用自然语言对比两次会话 | *“对比一下 r-9f3a 和 r-4d81”* |
| 对某次改动下判断 | *“精简 CLAUDE.md 有用吗？”*、*“那次改动值不值？”* |
| 对比两个时间段 | *“我现在的配置比上周更省吗？”* |
| 验证复盘给出的估算 | *“证明那次修复真的划算”* |

运行 ID 可从 **Runs（运行列表）** 页面点击复制，也可来自 `list_runs`。任何唯一前缀
都可用，因此 `r-9f3a` 与 `r-9f3a1c2b7e04` 等效。顺序无所谓：开始更早的那次运行
永远作为基线，所以不会因为写反顺序而把正负号搞错。

### 它做什么

1. 选择模式：按 ID 对比两次运行，或对比两个时间段。条件允许时两者都做，因为二者一致
   是能拿到的最强证据。
2. 在请求任何时间窗**之前**先检查 `get_data_retention`，当「改动前」那侧数据已被删除时
   如实拒绝，而不是悄悄换成一个更窄的问题来回答。
3. 调用 `get_harness_changes`，**主动给出**切分时间点，而不是要求用户回忆自己何时改的。
4. 运行 `compare_runs` 或 `compare_periods`，把差额归因到真正在动的那个因子，并与 harness
   差异交叉验证 —— 上下文变小且 CLAUDE.md 同时缩短，是一条成立的因果链；调用次数变少而
   harness 毫无变化，那多半只是任务更简单。
5. 报告时给出明确的置信度，当差额落在噪声范围内时直接说「无可测量差异」。

### 该用哪种模式

| | 两次会话 | 两个时间段 |
|---|---|---|
| **适用于** | 你刻意把同一个任务重跑了一遍 | 你只是继续正常工作 |
| **优点** | 精确 —— 两侧是同一份工作 | 把任务难度平均掉了 |
| **缺点** | n = 1；任务难度与缓存状态也在变 | 会被同期其他变化混淆 |
| **这样问** | *“对比 r-9f3a 和 r-4d81”* | *“对比本周和上周”* |

### 读懂三个因子

成本差异被拆成三个**精确相加**的因子：

| 因子 | 含义 | 常见成因 |
|---|---|---|
| **调用次数** | 你发起的 API 调用变多或变少了 | 任务规模，或某个工作流需要的回合更少 |
| **每次调用的 token** | 每次调用携带的上下文变多或变少了 | CLAUDE.md 改动、更精准的文件读取、交给子智能体 |
| **每 token 单价** | 模型与缓存的组合重新定价 | 换了模型，或缓存命中率变化 |

哪个因子在动，就是全部答案。上下文变小且 CLAUDE.md 同时缩短，是因果关系；调用次数
变少而 harness 毫无变化，通常只说明第二个任务更简单 —— 技能会直说，而不是抢功：

```
$107.84 → $42.44（−60.6%），API 调用 368 → 251 次。

调用次数          −$34.29  (52%)   368 → 251 次
每 token 单价     −$18.18  (28%)   混合单价 −30%
每次调用的 token  −$12.94  (20%)   259,548 → 213,899

置信度：低。这是两个不同的任务而非重跑，且 harness 差异为空 —— 因此调用次数这一项
大部分来自任务规模，而不是改进。站得住的数字是每次调用成本：−42%。
```

### 诚实性规则

工具会返回一个由数据生成的 `caveats` 数组 —— n = 1 提醒、两侧样本量失衡、窗口长度不等、
缺少快照、窗口被裁剪。技能必须把它们报告出来，这样结论的适用边界就不依赖模型是否记得提。
它不得从单一运行对推算月度数字；当两侧规模不同时，优先给出每次运行与每次调用的速率。

### 文件

```
assets/skills/ai-change-impact/

  references/
    interpretation.md      把各因子归因到成因、置信度阈值、何时该说「无差异」
```

## 完整闭环

两个技能合用的价值远大于分开用。一个完整周期：

1. **找到问题。** `/ai-usage-review` → *“全局 CLAUDE.md 有 3,180 token，约 $41/月。
   先做这件事。”*
2. **落地修改。** 接受它的提议，或自己动手改。文件变化时应用会记录一次 harness 快照，
   这就是之后的切分时间点。
3. **记下日期。** 技能会告诉你，你不必自己记。
4. **继续正常工作**，直到两侧都有足够数据 —— 几次会话，或几天。
5. **验证效果。** *“精简 CLAUDE.md 有用吗？”* → 技能从 `get_harness_changes` 找到切分点，
   对比其两侧的时间段，并报告「每次调用的 token」这个因子是否真的动了。

如果第 5 步给出**无可测量差异**，那也是一个真实答案：要么第 1 步的估算不准，要么改动
太小、在噪声里看不出来。在你基于同一套假设再改十处之前，这两点都值得先弄清楚。

### 注意保留窗口

所有实际计数 —— 技能调用次数、hook 触发次数、注入 token、对比窗口 —— 跨度都是
[保留窗口](../README.zh-CN.md#数据保留)，默认 30 天，而不是固定的一个月。对比的
「改动前」那一侧必须仍在窗口内。如果你打算衡量某次改动，尽量把它安排在窗口的靠前位置
而不是末尾；也不要指望调大窗口就能把已删除的历史找回来 —— 调大只会重新扫描转录文件，
因此只能恢复 JSONL 里仍然存在的部分。
